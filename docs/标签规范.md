# ShopCare 标签规范

标签规范服务于数据标注、模型训练和自动派单。程序的唯一事实来源是 `01-data/class.txt` 与 `01-data/label_meta.json`；本文件解释业务边界，不替代配置文件。

## 1. 标签总览

| 标签 | 含义 | 责任部门 | 基础优先级 |
|---|---|---|:---:|
| `logistics` | 运输、派送、签收、发货履约问题 | 物流仓储部 | P2 |
| `quality` | 商品缺陷、破损、功能异常、与描述不符 | 品控/供应商 | P1 |
| `after_sale` | 退款、退货、换货、维修及售后流程 | 售后部 | P1 |
| `invoice` | 开票、发票信息错误、重开、未收到 | 财务部 | P2 |
| `price_promo` | 价格、优惠券、活动、价保、赠品 | 运营部 | P2 |
| `payment_account` | 支付失败、扣款异常、订单状态、账号安全 | 技术支持 | P1 |
| `consult` | 商品参数、使用方法、安装、库存和规则咨询 | 客服中心 | P2 |
| `service` | 客服回复慢、服务体验问题或承诺未兑现 | 客服质检 | P1 |
| `invalid` | 无效输入、乱码或无明确诉求 | 归档处理 | P2 |

`invalid` 必须独占；其余 8 类允许组合。例如“商品坏了并且要求退款”标注为 `quality,after_sale`。

## 2. 标注优先级

1. 先判断是否存在可处理的有效诉求；无有效诉求时只标 `invalid`。
2. 再标事实类标签：物流、质量、发票、价格优惠、支付账号。
3. 再标用户诉求：退款、退货、换货、维修归 `after_sale`。
4. 最后判断咨询和服务反馈。

标签必须由文本明确支持，不靠推测补标签。一次反馈包含多个明确诉求时允许多标签，但不能重复语义。

## 3. 容易混淆的边界

| 表述 | 标签 | 判断依据 |
|---|---|---|
| “锅坏了” | `quality` | 描述商品事实 |
| “锅坏了我要退款” | `quality,after_sale` | 同时包含事实和处理诉求 |
| “退款一周没到账” | `after_sale` | 售后流程问题 |
| “钱扣了但订单未支付” | `payment_account` | 支付状态异常 |
| “想问退货规则” | `consult` | 尚未提出实际售后申请 |
| “说好买一送一但没送” | `price_promo` | 营销承诺未兑现 |
| “客服不回复且快递未到” | `service,logistics` | 两个独立问题 |

## 4. 情感、优先级与复核

情感由 `08-sentiment` 词典和规则引擎输出 `positive`、`neutral`、`negative`。优先级由 `09-priority` 根据基础优先级、情感系数、升级关键词和多标签加分计算，输出 P0/P1/P2、SLA 和复核建议。

低置信度工单不是“分类失败”，而是主动拒识。系统先检查单标签激活阈值，再检查整体平均置信度；不满足条件时进入外部推理或人工复核。

## 5. 标注质量检查

正式数据建议采用双人独立标注，对分歧样本进行仲裁，并统计 Krippendorff's alpha。提交前运行：

```bash
python tools/check_dataset.py
python 01-data/data_eda.py
```

新增标签时应追加到 `class.txt` 末尾、同步更新 `label_meta.json`、补充训练数据并重新训练所有模型。不要调整已有标签顺序，否则旧模型输出维度会失效。
